# Desktop GPU primary: reusable entrypoints and stage boundaries

This is a source map only. No workload, build, or device run was performed.

## Reusable main-flow entrypoints

- `scripts/experiments/assistant_local_api_pilot.py` is the closest reusable Python full-stack assistant main. `_request_and_check_history` sends the same typed `OrchestratorProcessRequest` through either the internal bus or Gateway API, then checks persisted session history. `attempt` supplies fresh request/session/correlation IDs and records one caller-side monotonic interval. The current bounded pilot supports up to 10 total requests; its `--main-session` preset is exactly 5 warmups plus 100 measured requests with a 600–7200 second cap. It is not the approved 900-request cumulative TTS/LLM/STT campaign as-is.
- `scripts/hosted_peer_e2e.sh` plus `tests/e2e/hosted_peer/hosted-peer-live-shell.spec.ts` is the existing browser/mesh main path. The matched CPU campaign runner invokes the exact “matched mesh Assistant request pilot records fixed typed replies” test and reads its JSON attachment. It verifies a typed reply and history through the browser/peer path; the browser timing is a separate requester-side clock.
- `scripts/experiments/assistant_measurement_records.py` already provides immutable request rows, grouping by workload/model/config/source/route/surface/session, and Type-7 summaries. Its row is one whole request span; it has no stage/provider span schema.

The existing CPU campaign runner is `docs/experiments/tcc-20261013-submission-20261030/root/matched-main-campaign-v319/campaign-runner.py`. It counterbalances local/API/mesh, with 5 warmups and 100 measured requests per cell. Keep that CPU campaign sealed and unchanged. Desktop GPU needs its own independently identified condition and full denominator.

## Existing boundaries and missing spans

| Stage | Existing source boundary | What can be observed now | Missing for a joined desktop GPU main |
|---|---|---|---|
| STT | `app/services/stt_transcription/service.py`, `transcribe_audio` / `transcribe_sync` | Model invocation start/end lifecycle events when the observer is installed; current `elapsed_ms` is computed with `time.time()`. Response fields include audio duration, not processing latency. | A monotonic per-request STT span joined to the later assistant request through stable request/correlation IDs, plus actual selected provider/model binding. Do not mix STT wall-clock elapsed with monotonic request spans. |
| LLM / assistant | `app/services/orchestrator/service.py`, `process_external_input`, `_process_input`, `_process_streaming_input`, `_invoke_inference_llm`, `_stream_inference_llm` | Whole typed reply/correlation and assistant stream events; the local/API pilot captures caller start through typed reply and checks DB history after the measured end. | Monotonic provider invocation and completion span, with actual backend/model identity and joined request/session/message IDs. The existing record is the end-to-end assistant request only. |
| Tools | Orchestrator graph inside `_process_input` / `stream_graph_events`; `process_tool_result` is not a universal timing boundary | Tool results/events can be reflected in the graph/assistant response. | Per-tool dispatch/start/end and provider identity tied to the same turn, without treating a graph callback as a universal span. The current pilot workload is a typed assistant answer, not a tool-turn measurement. |
| TTS synthesis | `app/services/tts/service.py`, `_play_text`, `_synthesize_to_bytes`, `synthesize` | `synthesize` reports audio duration (derived from bytes/sample rate); stream lifecycle exposes started/completed behavior. Audio duration is not synthesis latency. | Monotonic provider synth start/end and selected TTS engine/model joined to the assistant turn. Existing TTS request IDs are not inherently the originating LLM request ID on the standalone `_on_tts_request` path. |
| Playback / audio output | `app/services/tts/service.py`, `_play_audio_bytes`; TTS started/completion callbacks/events | Actual playback start and completion are observable as events/callbacks on the output service. | A monotonic playback interval and explicit join to the TTS synthesis and original turn. Do not count generated audio duration as playback completion or infer hardware output from a synthesized response. |
| Render / client | `tests/e2e/hosted_peer/hosted-peer-live-shell.spec.ts` | `requesterDispatchToTypedCompletionMs` is a browser-side elapsed duration for the mesh main. | For desktop GPU, record render receipt/completion as a separate client-local duration and correlate IDs. Never subtract client and Python timestamps or compare absolute wall-clock times across processes. |
| History | `assistant_local_api_pilot.py::_request_and_check_history`; Orchestrator `_persist_chat_message` | Persisted history is checked after the typed response in the pilot; this is a correctness predicate outside its latency span. | If history latency is a reported stage, measure the history read/write with its own monotonic boundary. Preserve the current definition that response latency ends before the history verification read. |

Gateway `route_generator.py::dispatch_validated_body` validates/authorizes and calls the typed handler, but exposes no stage timestamps. Gateway WebRTC RPC similarly dispatches through the bus and has an overall timeout, not a per-stage timeline. Existing outer IDs and route boundaries are useful correlation anchors, not stage telemetry.

## Campaign alignment and readiness

The planned desktop GPU primary should preserve the approved independent-condition protocol: CPU extra remains unchanged; run desktop GPU as a separately sealed condition; hold measured cross-device/surface comparisons until both conditions finish and seal. Each new condition needs its own approved warmups plus 900 measured requests, with the cumulative stages TTS, then TTS+LLM, then TTS+LLM+STT. The later shared-provider local+mesh contention phase is expected and must be labeled as contention, not exclusive GPU baseline. iOS is excluded from the active comparison.

For GPU attribution, capture the actual selected backend, offloaded layers, GPU utilization/device, and resource baseline for the run. A configured GPU backend alone is not evidence that inference used the GPU. Keep stage durations within their own process/clock domain and retain request/session/correlation/message joins.
